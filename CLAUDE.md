# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Data Flow Visualization is a **client-only static web app** that turns a small
declarative DSL into an interactive data-flow diagram. The DSL text is the single
source of truth; parsing, validation, layout, and rendering all run entirely in
the browser. No backend is required.

Live demo: https://popovdk.github.io/data-flow/

## Commands

```bash
npm install          # install dependencies
npm run dev          # start Vite dev server (runs generate:parser first via predev)
npm run build        # production build to dist/ (runs generate:parser first via prebuild)
npm run preview      # preview the production build
npm run generate:parser  # regenerate src/dsl/parser.generated.ts from grammar.pegjs
```

There is no test runner, linter, or standalone typecheck script configured.
Type safety relies on `tsc`'s strict settings via the editor/IDE (`tsconfig.json`
has `noEmit: true`); Vite does not type-check during `build`.

## Build pipeline / generated parser

- The DSL parser is generated by **Peggy** from `src/dsl/grammar.pegjs` into
  `src/dsl/parser.generated.ts` by `scripts/generateDslParser.mjs`.
- `parser.generated.ts` is **gitignored** and carries `// @ts-nocheck`. Never edit
  it by hand — change `grammar.pegjs` instead and re-run `npm run generate:parser`.
- `predev` and `prebuild` npm hooks generate the parser automatically, so a fresh
  clone works with just `npm run dev` / `npm run build`.

## Language policy (hard rule)

All documentation, specs, and code comments MUST be in **English**, even when the
prompt/discussion is in Russian. UI strings may be localized later, but code
identifiers and comments stay English.

## Architecture — Functional Core / Imperative Shell

Keep the boundary between pure core logic (no DOM) and the imperative shell (DOM,
events) clean.

**Core (pure-ish, no DOM access):**
- `src/dsl/grammar.pegjs` — PEG grammar (source of the generated parser)
- `src/dsl/parser.ts` — `parseDsl`: DSL text → AST
- `src/dsl/validator.ts` — `validateDiagram`: AST → diagnostics + model
- `src/dsl/types.ts` — AST/model + diagnostics types
- `src/diagram/graph.ts` — `buildGraph`, `bundleConnections`, `computeHighlight` (field graph, cycle-safe traversal, bundling)
- `src/diagram/layout.ts` — `computeLayout`: positions + routes (uses Dagre)
- `src/diagram/diagramBuilder.ts` — `DiagramBuilder`: parse → validate → build pipeline
- `src/diagram/types.ts` — graph/layout/result types

**Shell (DOM / event-driven):**
- `src/editor/editorController.ts` — CodeMirror 6 integration
- `src/render/renderer.ts` — native SVG rendering
- `src/render/diagramController.ts` — interaction + zoom/pan (`@panzoom/panzoom`)
- `src/shared/` — `persistence.ts` (localStorage), `exporters.ts` (SVG/PNG export), `debounce.ts`
- `src/app/` — composition root and UI wiring (`appController.ts`, `toolbarController.ts`, `diagnosticsRenderer.ts`, `dom.ts`, `constants.ts`, `examples.ts`, `initialDsl.ts`)

**Entry points:**
- `index.html` → `src/main.ts` → `src/app.ts` (`initApp`) → `AppController`
- `src/dsl/index.ts` and `src/diagram/index.ts` are the public barrels for those modules — import from them.

## Code conventions

- `strict: true`. Avoid `any`; prefer `unknown` + narrowing.
- Prefer **named exports**; avoid default exports.
- `PascalCase` for types/classes, `camelCase` for values/functions/filenames, `SCREAMING_SNAKE_CASE` for constants.
- Use `type` for unions/intersections, `interface` for extendable object shapes.
- Explicit return types on exported functions.
- Small, single-purpose, pure functions in core modules. Prefer early returns; line length ~100.

## Error handling & diagnostics (no exceptions for control flow)

- Parsing/validation return explicit values: `diagram` (or `null`) + `diagnostics: Diagnostic[]`.
- A `Diagnostic` has `severity` (`"error"` | `"warning"`), an English `message`, and 1-based `line`/`column`.
- Accumulate multiple diagnostics rather than failing fast (especially in validation).

## Security (XSS — hard rules)

- Treat DSL input strictly as data.
- Never use `innerHTML` for user-provided strings. For SVG/HTML text use `textContent` or `Text` nodes.
- Never evaluate user input: no `eval`, no dynamic `Function`, no script URLs.

## UI/UX rules

- Default "calm" view is minimal: thin, gray bundled (node-to-node) edges.
- On hover/selection, highlight the full path and dim unrelated elements via opacity. Reverse traversal (upstream) is always included.
- Click a field to pin the highlight; click it again to clear.
- Keep the **last valid diagram visible** when the DSL temporarily becomes invalid.

## Performance

- Debounce parse/validate/render updates (~300–500ms).
- Use event delegation; avoid per-field listeners for large diagrams.

## Data model glossary

- **Node** — a diagram box with fields
- **Field** — a named datum, possibly nested
- **FieldPath** — dot path to a (nested) field, e.g. `body.username`
- **Group** — labeled column of nodes (laid out left→right in declaration order; nodes stacked vertically)
- **Connection** — directed edge `sourceField -> targetField`
- **Bundle edge** — node-to-node aggregated edge shown in the calm state

## DSL quick reference

```text
group Backend [label="Backend API"] {   // optional grouping into columns
  node Request [label="Public API"] {    // optional [label="..."]
    body {                               // nested fields via braces
      username: String
    }
  }
}

node Auth {
  user: String
}

Request.body.username -> Auth.user       // connection: source -> target

// line comment   (also: # line comment)
```

- Identifiers (node IDs, field names): `[a-zA-Z_][a-zA-Z0-9_]*`; field paths use dot notation.
- Types are display-only (allowed chars: letters, numbers, `_`, `<`, `>`, `[`, `]`); they do not affect graph logic.
- Validation errors: duplicate node IDs / field names; connections referencing missing nodes or field paths.
- See `src/app/examples.ts` for a larger realistic example.

## Constraints

- Client-only; no backend for core functionality.
- SVG export is required; PNG export is optional/secondary.
- Cycles in the field graph are allowed — traversal must stay cycle-safe.
